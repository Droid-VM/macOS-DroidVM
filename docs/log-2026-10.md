### 主线 A：延续 UniXNU / DroidVM 的源码 XNU 路线

- 默认先评估现有 23G93 根盘与 DroidVM 内核组合，复用 ios 已有 Gunyah 引导、FDT→ADT、MMIO 和 App 经验。
- 明确记录 iPadOS kext 与 macOS 用户空间混合的兼容风险；同属 Darwin 23 不足以证明 Mach、IOKit、AMFI、APFS 或图形 ABI 匹配。
- 若混合组合在核心 ABI 上不可维持，建立匹配 macOS 内核/组件的候选配置，给出具体不兼容证据后再切换；不持续堆叠无边界 stub。
- 第一条实机路径优先评估 ios 已用的 MMIO 栈；本仓库 PCI overlay 保留为独立候选，必须显式选择设备/驱动组合，不把两条路径的验证结果混用。

### 研究 B：Snapintosh 式原版 kernelcache / monitor 路线

- [ ] 核对本机 Gunyah 是否允许所需嵌套虚拟化、异常/系统寄存器陷入、stage-2 控制及 NV2 状态；实际 guest 能力与物理 CPU 能力分别记录。
- [ ] 列出 SPTM/TXM、AIC、时钟、存储、DART 等合约如何映射到 Gunyah/crosvm，哪些需要 hypervisor 改动。
- [ ] 若无必需的 EL2/NV2 能力，将该路线标为当前平台阻塞；不能把 monitor 当普通 EFI/EL1 payload 直接执行。
- [ ] 若能力可满足，单独规划最小入口与页表验证，不改动主线已知良好启动包；macOS 27 的 KDK、AuxKC、驱动 ABI 与 23G93 分开锁定。

本轮优先 A；B 只做可行性判定。影子页表是由 monitor 实现的机制，不会自动消除主线源码 XNU 的 4 KiB 适配工作。

## 7. P4：WindowServer、显示、Metal 与真实交互

Snapintosh 的 26A428 证据表明 WindowServer 等待 Metal 设备后会退出，boot framebuffer 不能替代合成器。23G93 的行为必须实测；**不预设 simplefb/软件渲染必定能启动桌面**。按用户最新目录约束，图形专项设计、接口表和结论统一写到本项目 `docs/gpu/`（拟新增），不写入 `../win3d/docs/`；本节仅跟踪任务，新增专题文档后在此补具体链接。

- [ ] 先验证 GOP/simplefb 的格式、stride、范围、刷新及 App 呈现；分别保存内核 framebuffer 与 App 画面证据。
- [ ] 按 23G93 的 WindowServer 实际查询建立显示、IOSurface、IOGPU/Metal 服务需求表，定位第一个缺失合约。
- [ ] 比较 UniXNU NativeMetal 前端、Snapintosh AdrenoMetal/IOGPU 与现有 DroidVM 虚拟 GPU 的可复用部分；核对 macOS ABI、shader compiler、资源生命周期、同步与呈现。SM8750 和 X2-90/A740 的硬件差异不以驱动名称推断兼容。
- [ ] 优先评估 guest 前端→虚拟协议→Android host 后端；若选择 GPU 直通，另行证明设备所有权、SMMU/DMA、固件与 reset 能力，不在 guest 直接使用宿主物理寄存器。
- [ ] 最小图形验收按“设备枚举→真实绘制/回读→完成信号→WindowServer 接受设备→连续合成→App 可见帧”推进，不能只注册一个 Metal 名称。
- [ ] 确认 loginwindow、Finder、Dock 和 Terminal 实际显示；记录显示提交、完成/呈现、HID dispatch 计数，区分冻结画面、服务等待和输入未投递。
- [ ] 经 App 验证键盘、指针、点击、拖动、滚轮及窗口焦点；触摸需明确映射为 macOS 指针/手势的方式。
- [ ] 验证 System Settings 常用页面、窗口切换、文字/透明度/缩放；记录花屏、黑屏、失帧及 compositor 崩溃的具体场景。

验收：能登录并操作 Finder/Terminal/System Settings，连续交互期间画面与输入均前进；截图、进程存在和离屏三角形各自只算局部里程碑。

### 路线评估：借用 vma2（macOS）kext（2026-10-22，out/vma2/plan-sandbox.json）

- `scripts/fileset_kc.py` + `scripts/fileset-plan.py`：解析 `kernelcache.release.vma2`（MH_FILESET、arm64e、203 条目、链式重定位 format 8 共 575,950 处，其中 502,634 带认证位）。
- Sandbox 对内核/其他 kext 的绑定：指针 1482 处（→内核 332、AMFI 8、AppleMatch 4、IOStorageFamily 3）；**直接分支 2857 条（bl 2776、b 81；→内核 2806、AMFI 47、AppleMatch 4）；外部 ADRP 页引用 804 处**；非 hint PAuth 指令 334 条（BLRAA 309、BRAA 25，PAC 关闭时等同 BLR/BR）。AppleMatch：指针 38、分支 33、ADRP 16。
- 现有 NativePrelink 的前提是 kext→内核只经**数据指针**（`_PrelinkLinkKASLROffsets`），遇到外部 PC 相对编码直接拒绝；fileset 缓存里这些全是直接 BL/ADRP。要借用就得写一个二进制重定位器：外部 BL/B 经 veneer 转到原生内核符号（需 ±128 MB 内的跳板区）、804 处 ADRP(+ADD/LDR) 数据引用要成对改目标，而符号名来自 vma2 内核符号表→我们源码内核的导出表（缺 `_csr_check`），AMFI/IOStorageFamily 的目标还要在 iPad 缓存里按类名反查（iPad 缓存符号表为空）。工作量大且 ADRP 配对是启发式，易静默出错。
- vtable 填充：源码内核走 iOS 平台（`XNU_TARGET_OS_IOS`），`APPLE_KEXT_VTABLE_PADDING=0`；macOS kext 按 1 编译（OSMetaClass.h:165）。C++ IOKit kext 不能与当前内核混用；只有无 metaclass 的 Sandbox/AppleMatch 不受影响。
- PAC：Snapintosh 文档显示 X2E 的 PAuth 原生可用，其监视器只处理 PACGA；本项目 guest 里 arm64e launchd 的 pacibsp/retab 一直在原生执行、`arm64e-compat-log` 从未触发，PAuth 指令不是 UNDEF。PAC 关闭时认证指令不检查，已视为低风险（未在内核态验证）。

## 2026-10-26：开机慢（kc130→kc165 这一轮）的结论

这一轮只做一件事：查清「登录界面要 93 s（kc130）到 300 s+（kc132 以后）、guest top 却报 75~85% idle」的根因。结论是**两个独立问题**，一个已修并提交，一个已定位但未修（用户决定暂时不做）。

### 已修并提交：SIGPdisabled 从未清除 → 8 个 vCPU 空转

- 根因：XNU 只在核收到**第一个 IPI** 时清 `SIGPdisabled`（`osfmk/kern/machine.c:528`）。Gunyah 上我们的板级驱动从来不给核发 IPI，于是每个核的 `cpu_idle()` 每次进门就因 `idle_disallowed` 立刻返回，`machine_idle()` 立刻再进，8 个 vCPU 全速空转；guest 自己把这些时间记成 idle，宿主则是 800% CPU。
- 旁证：`idle-wfe=0` 单独改无效——`Idle_load_context()` 写在 `if (idle_proximate_timer_wfe == 1)` 外面，关掉 WFE 后不落 WFI 而是立刻回 `machine_idle`，变成更紧的空转。所以需要独立的 `idle_wfe_poll` 开关把三处一起门控。
- 修复（两处，都已验证）：
  - `patches/drivers/ArmCpu-idle-wfi.patch`（主仓库 `0983b9f`）：`gSelfIpi` 默认开，每个核从 `initCPU` 给自己发 SGI 0；`waitClear` 加轮询计数和 1 秒超时；`for(;;) wfe` 改成 `parkCore()`（WFI + 关 vtimer/ICC_IGRPEN1_EL1）；boot CPU 打 SMP step/fail 表。
  - `patches/xnu-12377/0010-idle-end-every-idle-path-in-WFI-on-the-virtual-mach.patch`（内核 `6136ce7`）：Gunyah trap WFI（vCPU 阻塞、宿主拿回物理核）但 WFE 在 guest 内本地执行，所以虚拟板的所有 idle 路径都以 WFI 结束；`idle-wfe=1` 可恢复 WFE 轮询做 A/B。pc-sample 增加 idle 分支报告（idle loop 进入次数、WFI 次数与阻塞 tick、四种出口、两种 idle_disallowed 原因）。
- 效果：loginwindow 85.0 → 73.4 s，WindowServer 85.2 → 74.2 s；宿主 idle 从 3% 升到 396%，vCPU 从 8×100% 降到只跑真实工作。

### GPU 每帧 12 ms 拆分（3681 个 K 行回归）

### 推翻"GPU 12 ms/帧"：时间在 VkCommandBuffer 边界上空等（kc231–kc239）
- gpu-bench（`overlay/metal/gpu-bench.mm`，以 `--probe` 代替 icon-probe：`/tmp/restage-bench.sh`）：1280x800 单 pass 私有纹理 填充 54 µs（~19 Gpx/s）/拷贝 98/9 采样模糊 223；IOSurface 慢约 3 倍（填充 157、拷贝 322、模糊 490）；每 pass 固定开销 13–20 µs。
- turnip `turnip passes` 按目标分类：拖动时 99% 像素画在 tiled+UBWC 的 RGBA16F（cpp8）中间纹理，**没有线性目标**——内存布局排除。
- turnip pass 级 GPU 计时（`tu-pass-timing=1`，build-turnip-macos.py：每个 render pass 前后 WFI+CP_ALWAYS_ON_COUNTER 写环形 BO，按首个 fragment shader 汇总；BO 要 sync_cache；pass 状态合并时字段要一起合并）。gpu-bench 校验：填充 40 vs 47 µs、clear 25 vs 33 µs，可信。
- 结果：拖动时每帧 render pass 真实 GPU 时间仅约 1.6 ms（最贵的模糊 fs `f17f16bb` 4079 指令也只 ~85 µs/pass）——**shader 不是瓶颈**。K 行的 12 ms 主要是每帧约 20 次、每次约 0.33–0.38 ms 的 GPU 空等。

### xzone 核实（kc262–kc263，2026-10-27）
- 起因：准备改 `vm_map_range_configure` 恢复 xzone 前先核实前提。libmalloc-812 开源码里 macOS arm64 走 CONFIG_MACOS_RANGES（自己在 16–63 GiB 预留，不读 vm.malloc_ranges），与"无 ranges → 无 xzone"矛盾。
- kc262：cpubench 打印 malloc(64) 地址 = 0x100c77fa0（不在 16–63 GiB）；子进程 `MallocReportConfig=1` 无输出——malloc_report 只在 stderr 是 tty 时写，要再加 `MallocDebugReport=stderr`。
- kc263：报告 `Enable Xzone Malloc: 1 / Reason: default`，XZM Config 里 Data Range 0x0/0、Pointer Range 1/2 基址 0（大小 ~8 GiB 两段 = 走的是 user-ranges 路径，vm.malloc_ranges ENOENT 后不建区间）；Thread Caching 开、Initial Slot Config CLUSTER/CPU、Reclaim Buffer ENABLED。
- guest 的 libsystem_malloc（/tmp/libmalloc，IDA）`malloc_config_from_input`：比开源版多了 "xbs chroot"（输入 +0x1A == 2）、"zero-on-free bincompat"（+0x80 = malloc_zero_policy ≠ 0）、"macOS bincompat list"（SDK<26 且在名单里）、IINA。malloc_zero_policy 来源：FeatureFlags `libmalloc/ZeroOnFree`（guest 里 Enabled）、boot-arg `malloc_zero_on_free_enabled`、SDK<13 的 macOS 程序置 2、环境变量 `MallocZeroOnFree`/`MallocZeroOnAlloc`。`MallocSecureAllocator` 只在 internal 策略下有效。
- 结论：内核补丁不做（区间只是隔离）。guest malloc 慢是 xzone + zero-on-free 本身的成本（与宿主 glibc 比不公平）。下一步 A/B：`MallocZeroOnFree=0`（→ magazine、不清零）对比默认。
- cpubench 现状：主进程跑完后起一个子进程（`MallocDebugReport=stderr MallocReportConfig=1`），子进程只打印配置就退出。
